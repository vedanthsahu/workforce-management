# SeatBook / Workforce Management — Learning Guide

This is the one to read, not grep — `SeatBook_PROJECT_REFERENCE.md` next to this file is the dense, lookup-oriented version. Both were produced by directly reading the real backend source (`backend/main.py`, `backend/core/*`, `backend/services/*`, `backend/repositories/*`, `backend/chatbot/*`, `backend/api/*`), across several passes, rather than reasoned from secondhand notes.

Read it in order.

---

## 1. The one-paragraph story

SeatBook lets employees book a desk, manage guest visits, and handle admin work (floor layouts, teams, roles, business rules) for a hybrid workplace, with a chatbot built into the same app so people don't need a second tool for simple requests. The two hardest engineering problems underneath that simple description are: making sure two people can't book the same seat at the same time under real concurrent load, and making sure retries (a flaky network, a double-click, a frontend bug) never turn into a duplicate or a lost booking. A third, quieter theme runs through almost everything else: wherever a human would otherwise have to do something repeatedly by hand — provision an account, re-type a hardcoded limit per customer, remember to not spam a user's database row on every click — the system was built to do it automatically instead, with a specific, nameable trade-off accepted each time.

## 2. Logging in — two separate paths that both lead here

A user signs in one of two ways, and it's worth knowing both exist, because they solve a real trust problem differently.

**Path A — direct Microsoft login.** The frontend redirects straight to Microsoft's own OAuth login page. Microsoft redirects back with an authorization code; the backend exchanges that code for an access token and an ID token, then verifies that ID token's signature against Microsoft's own public signing keys (fetched live, matched by key ID) — so the backend isn't trusting a token it can't independently verify.

**Path B — a company SSO gateway.** A second entry point redirects through an internal gateway (`apps.solugenix.com`) instead of straight to Microsoft. That gateway hands back its own wrapper token, and here's the interesting part: that wrapper is signed with a secret this backend does **not** hold, so it has no way to verify the wrapper's signature directly. Instead of trusting it blindly, the backend only acts on the **Microsoft Graph access token embedded inside** that wrapper — and that embedded token gets its trust the honest way, by being used to actually call Microsoft Graph. If it's forged or tampered with, Microsoft itself will simply reject it the moment the backend tries to use it. Trust is established by what the token can actually do, not by what it claims about itself.

**From either path, the rest is the same.** The backend asks Microsoft Graph for the user's profile, their reporting manager, and their distribution-list/group memberships. **Distribution-list membership decides the user's role** — nobody manually makes someone a Manager or a Facilitator; if the org's own directory says they're in the right group, SeatBook already knows. A JWT access+refresh token pair gets issued as cookies, and the user lands in the app, authenticated.

**And once that session exists, staying logged in doesn't cost a database write on every click.** A sliding-expiration mechanism pushes the session's expiry forward as the user keeps using the app — but it only actually writes to the database when the session's last-recorded activity is already more than a minute stale. Click around for five minutes straight, and that's one write, not three hundred. If that write itself ever fails for some unrelated reason, the failure is swallowed and the request proceeds anyway with the session it already had — extending a session is a nice-to-have on top of an already-valid request, never something allowed to break one.

## 3. The system most people would miss: this isn't "login does some Graph calls" — it's a full account-lifecycle engine

It's easy to read section 2, see "fetches a profile, creates a user," and move on — and in doing that, miss that what's actually built here is a genuine three-phase identity-and-team lifecycle system: automatic **intake**, automatic **update**, and continuous background **maintenance**, plus two separate manual override paths, all writing to the same tables with deliberately non-conflicting rules. This is the kind of thing worth describing as its own piece of system design in an interview, not a side note about login.

**Phase 1 — Intake (first login only, fully automatic).** Nobody provisions an account by hand. The role gets decided *before* the user even exists as a row: a live Graph group-membership check (with retries and backoff, so a transient Graph hiccup doesn't wrongly deny someone a role) returns Facilitator or Employee — and if that check isn't even configured, everyone defaults to the lower-privilege Employee, never silently defaults upward. The manager relationship gets resolved opportunistically: if the person's manager has *already* logged in before, they're linked by an internal user id immediately; if not, the relationship is recorded as a raw Microsoft object id and only resolves into a real link once the manager eventually logs in themself. And department does more than sit in a profile field — it **automatically assigns the person to a team**: an existing team with a matching name (case-insensitively) is reused regardless of how it was originally created, or a brand-new one gets minted and tagged as Graph-sourced so it's distinguishable later from a hand-created team. Every single field involved — email, display name, job title, office location, department, manager — is pulled out of Microsoft's raw JSON response by a named helper function and written by hand into three separate tables (the flat day-to-day columns, a wider enrichment table for the fields nobody queries often, and a provider-identity link table) — there is no Graph SDK model binder or ORM auto-mapping doing this for you anywhere in the path.

**Phase 2 — Update (every login after the first, deliberately narrower than intake).** A returning login does **not** re-check role, and does not rewrite the whole profile. It only re-syncs **department and team membership** — nothing else. If a correct answer matters here, it's "department/team sync happens on every login; role only changes via the background sync thread or an admin, never by logging in." This update is also deliberately fail-open: if Graph is down or the sync hits a database error, the error is swallowed and logged rather than ever blocking an otherwise-valid login.

**Phase 3 — Maintain: three always-on background threads that run for the entire life of the process, independent of anyone logging in at all.** Started once when the FastAPI app boots:
- A **role-sync thread** fetches an app-only Graph token (no user has to be logged in for this — it authenticates as the application itself), lists every member of the configured Graph group across every page of results, and scans every user in every tenant, promoting or demoting *only* between Employee and Facilitator — Manager, Front Office, and Tenant Admin are never touched by this automated path; those stay admin-assigned on purpose. Off by default, checks hourly by default.
- A **team-sync thread** does the same app-wide, full-directory scan for department, catching drift even for someone who hasn't logged in in months. Also off by default, also hourly by default.
- A **layout-cutover thread** (a completely different domain — see section 6 — but built with the exact same machinery) is *on* by default and checks every 5 minutes.

All three share the same careful engineering underneath, which is worth being able to describe precisely if asked "how would you build a safe background scheduler inside a web app process": daemon threads so they can never block the process from shutting down; a guard that checks whether a thread is already running before starting a new one, so a duplicate startup event can't double-launch it; waiting on an interruptible event rather than a plain sleep, so shutdown can wake the thread immediately instead of waiting out up to an hour; a fresh database connection opened per cycle rather than one held for the thread's entire life; and a try/except around each individual cycle so one bad run (a Graph outage, say) gets logged and skipped instead of permanently killing the thread.

**Any role change, from either source, forces the person to re-authenticate.** The background role-sync thread and the manual admin-override path (next) both revoke every one of that user's active sessions and write an audit event the moment a role changes. A stale access token carrying an old, now-wrong role claim can never quietly outlive the change — the user gets logged out and has to log back in to pick up the new permissions. That's not an accident; it's the same safety call made twice, independently, in two different code paths.

**Phase 4 — Manual override, for when an admin needs to act directly.** A Tenant Admin can hand-set someone's role or status. Three real guardrails sit in front of that: the highest-privilege role in the system can never be assigned or touched through this endpoint at all, by design — there's no in-app flow for it; only an explicit, named list of roles can even be assigned this way; and — this is the one worth remembering — **the system will refuse to let the last active Tenant Admin in a tenant be demoted or deactivated.** It counts how many other active admins would remain, and if the answer is zero, it rejects the change outright and logs the denial instead of silently locking everyone out of admin access.

**Phase 5 — Self-service profile edits, and a quiet but deliberate agreement between two independently-written code paths.** A user can edit their own name, display name, phone, and office location. For the two fields that overlap with what Graph also writes (phone, office location), the Graph-sync code only fills a blank value — it can never overwrite one that's already set — while the self-edit code's own update always wins when the user actually provides a new value. Put plainly: **the directory can only fill in what's missing; a person's own edit always takes precedence over the directory.** That's a rule two different pieces of code agree on without either one needing to know about the other.

**One honest wart:** one particular role name is stored in the database with a literal space in it ("FRONT OFFICE") instead of the underscore-separated style every other role and every other layer of the app uses, because a database check constraint was never updated to match. Two small helper functions paper over the mismatch at every place the code reads or writes that value, so the rest of the codebase never has to know about it.

**Why this is worth presenting as one system, in an interview, rather than disconnected facts:** without it, SeatBook would need a human to provision every new hire's account, manually assign their role, manually keep the org chart in sync as people move teams, and manually remember to revoke access whenever someone's role changes. Instead, the enterprise directory is treated as the one source of truth, re-checked continuously rather than fixed once at account creation — with explicit guardrails wherever a human could otherwise lock the system or themselves out, and explicit, auditable logging wherever access actually changes.

## 4. Who's allowed to do what — the real authorization model

Read the actual authorization code, and it's more interesting than "check if role equals ADMIN." The real rule, confirmed directly in the code's own documented history (including a reversed decision dated 2026-10-23), is a **resource-ownership model**, not a flat role check:

- For an **existing** resource (a booking that already exists, say), the rule is: you can act on it if you created it, if you're the person it's *for* (the subject), or if you're a **Tenant Admin** — admins get an unconditional bypass so they're never blocked from acting during a crisis, no matter who created or is the subject of the thing. Every other role's rights on an existing resource come only from actually being its creator or its subject — being, say, a Facilitator doesn't by itself let you touch someone else's existing booking.
- **Creating** something for someone else is a *different* question, because there's no existing resource to "own" yet — it's a plain role-based allowance. Only Tenant Admins and Facilitators can originate a booking for someone other than themselves; employees and front-office staff cannot.
- **Guest check-in/check-out is Front Office's job, and nobody else's** — not the visit's creator, not its host, not even a Tenant Admin. The code comment puts it plainly: front office is "basically the watchman on the door," and tracking who's physically in the building is their responsibility alone, not something a creator/host/admin substitutes for.
- The broader guest-domain surface (creating, modifying, cancelling, listing guests/visits/guest-bookings) belongs to Tenant Admins and Facilitators only — Front Office's entire positive permission list is exactly that one check-in/check-out line, nothing more.

**Why this is worth narrating precisely, not just "we have RBAC":** the ownership rule and the role-bypass rule are two genuinely different mechanisms stacked together, and getting them confused is exactly the kind of subtle authorization bug that causes real incidents. Being able to say "an admin bypass is unconditional; everyone else's access to an *existing* resource is ownership-based, and creating-for-others is a separate, role-based allowance" is a much stronger answer than "we check roles."

**The known gap, stated precisely:** every *enforcement* check above is a direct, hard-coded comparison against role-name strings (`TENANT_ADMIN`, `FACILITATOR`, `FRONT_OFFICE`, `EMPLOYEE`; `MANAGER` exists as a role but is explicitly commented as carrying no authority anywhere in this module — assignable, but dormant). But the `Roles`/`Permissions`/`RolePermissions` tables are **not** simply unused schema — `fetch_permissions_for_role()` genuinely queries them, and that result is attached as `user.permissions` on every login and every `/auth/me` call, so the frontend does receive a real, DB-backed permission list today. What's actually missing is the *other half*: nothing in `core/authorization.py` reads that list back to decide anything — every real access decision is the hard-coded role comparison, completely independent of what `user.permissions` says. So the honest, precise answer is "the catalog is queried and shipped to the client for UI rendering decisions; it just isn't wired into backend enforcement yet" — not "nothing touches those tables." A redesign toward a group-based permission model has been *planned* (role decides which groups you're eligible for; groups carry the actual permissions; UI-visible permission kept separate from backend-enforced permission; "who this applies to" kept as an independent setting from "what this permission allows") — but as of this read, none of that plan exists in application code yet, only in the database schema and design notes. "Designed, not yet implemented" is the accurate answer, not "we're migrating to it."

## 5. The hardest problem in the system: booking without double-booking or losing bookings

This is the part to know cold — it's the most sophisticated engineering in the whole project.

**The problem in plain terms.** Two people could try to book the same seat on the same day at nearly the same instant. A flaky connection or an impatient double-click could send the *same* booking request twice. Either one, handled naively, produces a bad outcome. The system solves both with two genuinely different mechanisms.

**Mechanism one — stopping two different requests from booking the same seat.** Right before the booking write happens, the backend takes a database-level lock scoped to exactly "this seat, on this date" (a Postgres advisory lock — no extra table row, it belongs to the current transaction and disappears automatically whether that transaction commits or rolls back). It then takes a *second* lock scoped to "this specific person, on this date," so the same person can't end up with two bookings on the same day via two near-simultaneous requests either. One detail worth knowing precisely: **there is no database constraint backing this up** — the code says so directly. The advisory lock is the *only* thing preventing the race; it's not a second line of defense behind a unique constraint. The two locks are always acquired in a fixed order — seat lock first, then the person lock — specifically so two different requests racing on two different seat/person combinations can never deadlock against each other.

**Mechanism two — stopping the same request, sent twice, from being treated as two different requests.** This is the idempotency ledger, and it's genuinely worth narrating as a small state machine:
- The frontend attaches a unique key to each booking attempt.
- Claiming that key is a real database insert that either succeeds or collides — not a "check if it exists, then insert" pattern (which would itself have a race in it). If two requests with the same key arrive at the same instant, the database's own uniqueness guarantee decides which one wins the claim; the loser catches that failure and looks at what the winner already recorded.
- If the key's never been seen: claim it, do the real work.
- If it's been seen with the exact same request body: hand back whatever was already decided the first time — no work repeated.
- If it's been seen with a *different* body: reject it outright, that's a genuine conflict, not a retry.
- If the original attempt looks like it's still running: say so (409), don't guess.
- If the original attempt looks abandoned — stuck for more than a minute — a reconciliation process runs instead of blindly retrying.

**The one design principle worth being able to state outright:** when the system genuinely can't tell what happened to an earlier attempt, it never guesses — guessing "it succeeded" when it didn't creates a phantom booking; guessing "it failed" when it actually succeeded risks a duplicate on retry. This is fail-closed by design, and it costs the user a worse experience in the rare ambiguous case ("please wait, check back") in exchange for the system never silently corrupting booking data. It's worth contrasting this directly against the fail-*open* choices covered elsewhere in this guide (section 2's session touch, section 3's department sync, the audit log's CloudWatch copy) — the direction isn't inconsistent, it's the same underlying question ("what does failure actually cost here") answered twice and landing on opposite answers, because booking correctness is expensive to get wrong and a one-cycle-stale profile field or session timestamp isn't.

**How reconciliation actually proves its answer — this is the detail that separates "I used an idempotency key" from "I understand why it's correct."** When an abandoned attempt needs resolving, the reconciler doesn't just check how much time has passed — it goes and acquires the **exact same locks** the original attempt would have needed to finish, then re-reads the ledger row *while holding that lock*. The reasoning: simply acquiring the lock only proves nobody is actively using it *right now* — it doesn't by itself prove the original attempt never completed. The re-read is what actually proves it: because a successful booking write and its ledger "succeeded" update always commit together in one transaction while holding that exact lock, if the lock is free and the ledger still doesn't say SUCCEEDED, there is nothing left anywhere that could still complete it. That's a proof, not an inference from elapsed time.

**The real "fencing" guard that protects the final commit.** The step that actually marks an operation SUCCEEDED is a conditional database update — "update this row, but only if it still has the exact version-stamp I saw when I claimed it." If a reconciler reclaimed that same row out from under a slow, still-running original request (because it looked abandoned), that update affects zero rows, and the original request's booking write gets rolled back on the spot instead of being committed after the fact. The comment in the actual code says it best: this conditional update is "the real ownership check — not the earlier claim — because it's the last thing that runs before commit."

**One more precise detail worth having ready:** the deadlock-avoidance ordering invariant is "seat lock before person lock" within a single booking attempt — nothing broader than that. The idempotency claim itself happens *before* any advisory lock is taken at all; the advisory locks are taken only once the request is past the ledger-claim step and into the actual business logic.

## 6. Floor layouts: draft, published, archived — a scheduled cutover, and a naming convention doing real work

The lifecycle most people would guess is: an admin edits a draft, then clicks publish, and the published layout becomes the one live layout for that floor, with the previous one superseded. That part's correct. The upload itself is validated with an explicit allowlist of permitted SVG elements/attributes (not a denylist trying to catch bad patterns — allowlists avoid the class of bypass a denylist regex is always chasing one step behind).

What's easy to miss: layouts can also be **scheduled to publish automatically at a future time**, and a background thread — running continuously in the same process since application startup — periodically checks for any draft that's due and promotes it without anyone clicking anything at the moment it happens. So "who published this layout" doesn't always have a human answer.

**A smaller but genuinely clever detail, at the moment a layout is uploaded, not published:** every seat gets its `seat_type` guessed automatically from a naming convention already baked into the SVG itself. A seat id like `HYD-PRV-F11-MR-C6-01` tells the parser "this is a meeting room, capacity six" — no admin has to go click through every cabin, meeting room, and training room after an upload to set that manually. Worth knowing the trade-off alongside the convenience: the exact same parsing logic exists a second time, independently, in the frontend's TypeScript, purely to compute the live "N seats, N cabins, N meeting rooms" count shown in the upload preview before anything is even saved. The two copies are kept in sync by a code comment pointing from one to the other, not by any shared definition — a small, real risk that a future change to the naming convention on one side quietly stops matching the other.

## 7. Two more subsystems that quietly remove manual work: blocked seats, and the business-rules catalog

**Blocked seats — a seat-maintenance system, entirely separate from floor layouts.** A seat can be taken out of the bookable pool for a date range without touching the floor plan at all — think "this desk is being cleaned/repaired/reserved for an event next Tuesday," as opposed to "the floor plan itself changed." Before a block is allowed, the system checks for existing bookings in that window first (blocking a seat never silently cancels someone's existing reservation out from under them), and how far in advance a block can even be scheduled is itself a tenant-configurable setting, not a hardcoded number (see next). Creating a block fires an admin notification as a background task, not inline in the request — so blocking a seat doesn't make an admin wait on an email send to get their response back.

**A per-tenant business-rules catalog — because almost every "how far in advance" number in this app used to be a hardcoded constant.** Booking advance windows, block advance windows, how long a draft/archived/deleted floor layout stays visible, how many rows the admin dashboard's activity feed shows, even a tenant-level on/off switch for whether employees can use the chatbot at all — every one of these is now a per-tenant key in a database-backed catalog instead of a constant buried in a Python file. **The one genuinely elegant piece of this:** the minimum safety gap before a scheduled floor-layout cutover isn't stored as its own setting. It's calculated fresh, every time, from two *other* settings (the employee booking window + a safety buffer) — specifically so nobody can update one of those two numbers later and accidentally leave a stale, now-wrong gap sitting around as a third value nobody remembered to update. And the floor on that buffer (it can never be zero or negative, or a layout could cut over the same day a booking is still pending against the old one) is enforced in *two* places on purpose — once in application code, once as an actual Postgres `CHECK` constraint — so even a bug that skips the application check still can't produce an unsafe value in the database.

## 8. Notifications, file storage, and audit logging: three places the same engineering instinct shows up

These three subsystems look unrelated on the surface, but reading them side by side, the same underlying habit shows up in each: **build the shared piece once, centrally, and reuse it everywhere, rather than reimplementing a judgment call at every call site that needs it.**

**A shared email/notification layer.** When the system emails someone — a booking confirmation, a blocked-seat alert to admins, a floor-layout publish notice — every one of those emails goes through the exact same rendering and recipient-resolution logic. Two things about it are worth remembering: the template engine is deliberately configured to **fail loudly** if a template references a variable nobody provided, rather than silently sending an email with a blank gap in it; and "who counts as an admin, for notification purposes" is defined in exactly one place and reused by every single "notify all admins" event, specifically so two different features can never quietly disagree about who an admin even is.

**Floor-layout storage is a private S3 bucket with freshly-generated, short-lived links — not a public file host.** The uploaded SVG (already sanitized against the XSS allowlist from section 6) goes into a bucket that isn't publicly reachable at all. What gets stored in the database looks like a normal URL, but it only actually resolves because every single response that includes it runs through one shared function that mints a brand-new, time-limited signed link on the spot — never the same link twice, and nothing to go revoke later, because it simply stops working once its short window expires. The retry logic wrapping these S3 (and SES) calls is itself deliberate about what counts as worth retrying: only actually-transient failures — throttling, timeouts, a 5xx from AWS's side — get retried; a permissions error or bad input never does, because retrying it would just waste time reproducing the same failure. And the AWS credentials/secrets this all depends on are fetched once and cached, not re-requested from Secrets Manager on every single call site that needs one — the one cost of that choice being that a rotated secret doesn't take effect until the process restarts, which is an acceptable trade for something that happens rarely and on purpose.

**Audit logging is a dual-write, deliberately decoupled, with a real redaction layer on the way back out.** Every audited action writes a row to the actual audit table (the record of truth) *and* emits a best-effort structured log line toward CloudWatch — wrapped so that a logging hiccup can never take down the real database write. And before any of that audit detail reaches an admin screen, a recursive scan strips anything that looks like a password, token, secret, or credential, at any nesting depth, replacing it with a redaction marker — plus the raw internal failure reason for a denied action is summarized into a plain sentence instead of being echoed back verbatim. That same instinct — full detail stays server-side/in logs, only a sanitized version ever reaches a client — shows up again in two completely unrelated corners of the codebase: a terminal-only error printer that's explicitly never wired into an API response, and the SSO login flow's own error handler, which logs the real provider error and redirects the browser to a generic error code instead. Three different layers, independently landing on the same rule.

## 9. Guest visits and guest bookings — two linked lifecycles, and booking modification as a traceable chain

A guest's **visit** (are they coming, when) and their actual **seat booking** aren't always the same lifecycle — a visit can shift without the booking needing to change, and vice versa. They're modeled as two separate, explicitly-linked entities rather than one merged object, specifically so situations where they diverge can actually be represented. Front Office owns check-in/check-out for visits exclusively (section 4); Tenant Admins and Facilitators own the rest of the guest-domain surface.

**Booking modification** does not cancel-and-recreate a booking when it's modified. A modified booking creates a new row that keeps a forward link back to the original via a single column, `modified_from_booking_id` — there's exactly one link, pointing backward from the new booking to the one it replaced; reading forward ("what did this booking turn into") just means looking for whichever row names this one as its `modified_from_booking_id`. The reason this exists at all: cancel-and-recreate would make a modified booking indistinguishable, in the data, from two unrelated bookings that just happen to be close together — the link preserves the fact that it's a continuous history of the *same* booking. The same "show it as modified regardless of its literal status" display rule gets applied a second time, independently, in the admin dashboard's own activity feed — two call sites agreeing by convention rather than by sharing one function, which is fine today but worth knowing about if the rule ever needs to change.

## 10. The chatbot — and a real architecture problem that *was* fixed, not one that's still open

This is a genuinely strong interview story either way it's told, and worth understanding both the "before" and the "after."

**What the chatbot actually is today:** it lives inside the same app, behind the exact same login — there is no second account, and, reading the actual route code directly, no second authentication mechanism either. Every chatbot endpoint uses the identical `get_current_user` dependency every other route in the app uses, and the identical per-request database connection every other route gets. When the chatbot needs to actually act on a booking rather than just talk about one, it calls the main app's own service functions **directly, in the same process, as ordinary function calls** — not over HTTP, even internally.

**What it apparently used to be, based on the code's own documentation of its history:** the code that binds a chatbot request's context carries an explicit note that it *used to* mint a short-lived JWT and open an HTTP client so the chatbot could call back into this same running application over a real network request — purely to re-authenticate as the same user it already knew it was — and that this round-trip has since been removed in favor of direct, in-process calls. That older design is exactly the kind of thing that can cause the double-connection-pool and skipped-revocation-check problems that show up in incident post-mortems: two authentication paths that can drift out of sync, and, if the chatbot's session machinery had ever used a separate connection pool from the main app's single-connection-per-request pattern, two independent pools competing for the database's finite connections under load.

**The honest way to use this in an interview:** don't claim credit for "fixing a production outage" unless you can describe exactly what you changed and verified — but it is completely fair, and a strong answer, to say: "the chatbot used to re-authenticate over a real HTTP call back into the same running app just to act as the current user, which is the kind of design that causes exactly the problems you'd expect — duplicated auth logic that can drift, and a second thing competing for database connections. That's been replaced with direct in-process calls sharing the same request's connection and the same auth dependency as every other route." That is a concrete, verifiable claim about the code as it exists today, and a much better story than asserting a gap that a direct read of the code shows has already been closed.

## 11. State management — the pieces that actually persist, and for how long

- **Login session state** — JWT access + refresh tokens, cookie-based, with the refresh-token and session tables explicitly created and swept for expired rows every time the app starts up, and kept alive by the throttled activity-touch from section 2 rather than a write on every request.
- **The idempotency ledger** (`idempotent_operations`) — scoped to exactly one operation attempt, keyed by the caller-supplied idempotency key. This is request-level dedup state, not identity state; its own claim → replay → reconcile machinery (section 5) is independent of whether the user is logged in.
- **Floor layout state** — a simple draft/published/archived status per layout, with the scheduled-cutover mechanism (section 6) as the one less-obvious wrinkle in an otherwise simple tri-state model.
- **Booking state** — not a single mutable row once modified; a forward-linked chain via one column (section 9), so a booking's current state has to be resolved by following the chain, not by reading one row in isolation.
- **Chatbot session/message state** — lives in the same database, read and written through the same per-request connection as everything else (section 10) — not a separate store, and not a parallel session concept that never talks to the main app's own session validation.
- **Background-sync state** — role sync and department/team sync aren't triggered by any request at all; they're continuously-running daemon threads started at application boot, each on its own interval, independent of any specific user's login (section 3).
- **Blocked-seat state** — a seat-maintenance status per (seat, date range), entirely independent of floor-layout state (section 7) — a seat can be blocked without any layout change, and vice versa.
- **Business-rule state** — a per-tenant key/value catalog (section 7) that other state machines *read from* (booking windows, layout-cutover timing) rather than hardcoding; falls back to a safe default if a key hasn't been seeded yet, rather than failing.
- **Audit-log state** — every sensitive action writes one `audit_logs` row (the record of truth) plus a best-effort structured log line to CloudWatch (section 8); the two are deliberately decoupled so a logging failure can never block or lose the actual DB write.

## 12. Interview questions you should be able to answer cold

**"Walk me through what happens when two people try to book the same seat at the same time."**
→ Section 5, mechanism one: the seat-then-person advisory lock pair, and the explicit fact that no DB constraint backs it up — the lock *is* the safety net.

**"How do you handle a user double-clicking submit, or a retried request?"**
→ Section 5, mechanism two: the idempotency key state machine, and be ready to explain *how* reconciliation proves non-completion (acquire the lock, then re-read the ledger) rather than just "it checks if it's been a while."

**"How does your authorization model actually work?"**
→ Section 4. Lead with the ownership-vs-role-bypass distinction, not "we have roles." Be precise about the Roles/Permissions catalog: it's queried and shipped to the frontend as `user.permissions` already, it just isn't wired into backend enforcement yet — don't say "nothing uses those tables."

**"Describe a system you designed, end to end, beyond just the code."**

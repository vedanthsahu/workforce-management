# eFACiLiTY Seat Booking Chatbot

Deterministic seat-booking chatbot for eFACiLiTY, with a FastAPI backend, a Next.js browser widget, and WhatsApp webhook support.

The chatbot does not use an LLM. It routes user input through rules, normalization, entity extraction, optional pgvector semantic fallback, and a deterministic booking state machine.

## Current Capabilities

- Three browser menu actions: `Quick Book`, `Book a seat`, and `My Bookings`.
- Optimized Quick Book journey: `Quick Book` -> select date -> confirm booking when a preferred seat is available.
- Quick Book ranks seats by favorites, most frequently booked seat, most frequently used location/floor, then recency.
- Full guided `Book a seat` flow for choosing date, office/site, building, floor, and seat.
- Browser My Bookings UI with `Upcoming`, `Past`, and `Cancelled` tabs.
- Upcoming bookings show modify/cancel actions when allowed.
- Past bookings show an `Expired` status and support direct `Rebook`.
- Rebook uses a calendar with color-coded dates for same-seat availability, unavailable dates, and dates where the user's existing booking can be changed.
- Future booking dates are highlighted separately from today and past dates for faster mobile scanning.
- Past and cancelled booking prompts are supported by free text.
- Today/current ongoing bookings are protected from modify/cancel actions.
- Free-text support for natural booking, list, modify, cancel, greeting, help, typo, and contextual prompts.
- WhatsApp channel uses the same backend booking engine.
- Session and backend connection errors use friendly recovery messages instead of generic failures.
- Responsive Playwright regression suite covers representative iOS and Android viewport profiles.
- Admin telemetry tracks intent confidence, user journey steps, seat-backend API calls, duplicate calls, latency, and bounded memory usage.

## Architecture

| Layer | Technology | Purpose |
|-------|------------|---------|
| Browser frontend | Next.js, React, TypeScript | Chat widget, rich cards, forms, booking cards |
| Backend API | FastAPI, Python, SQLAlchemy async | Chat APIs, webhook APIs, state-machine routing |
| Chat engine | Python deterministic state machine | Booking, Quick Book, My Bookings, validations |
| Seat backend bridge | External eFACiLiTY API | Sites, buildings, floors, seats, bookings, auth refresh |
| Database | PostgreSQL with pgvector image | Chat sessions, context, messages, menus, identity mappings |
| Cache/session memory | Redis | Active session/context and WhatsApp state |
| Observability | Elasticsearch/Kibana | Conversation logs and inspection |
| Runtime | Docker Compose | Local development services |

Seat-management data is not stored locally. Sites, buildings, floors, seats, and bookings are read/written through the external seat-management backend API.

## Environment

### Operational logging

Set `LOG_LEVEL=INFO` for normal local and deployed operation. Every chatbot API request emits a correlation-friendly line containing:

- UTC/local timestamp, severity, service, and logger name.
- `request_id` (accepted from `X-Request-ID` or generated by the API).
- HTTP method, path, status, outcome, and elapsed milliseconds.
- Authentication result and non-secret user/tenant identifiers.
- Chat session/message lifecycle, state-machine nodes, response types, and latency.
- Seat-backend method/path/status/latency and Elasticsearch indexing failures.

The API returns the same request ID in the `X-Request-ID` response header. Search that value across the chatbot logs to trace one request end to end. When the repository startup script is used, chatbot API output is available under `.local-run/chatbot-api.out.log` and errors under `.local-run/chatbot-api.err.log`.

Operational logs do not include bearer tokens, cookies, raw browser chat text, raw WhatsApp text, or backend error response bodies. Full conversation events remain controlled separately by `ENABLE_ELK_CONVERSATION_LOGS`.

### WhatsApp security configuration

WhatsApp is disabled by default. Before enabling it, configure a strong webhook
verify token, the Meta access token and phone-number ID, and the same
`MAIN_APP_JWT_SECRET` used by Workforce Management. Every permitted sender must
be mapped to a real Workforce identity using the exact normalized E.164 number:

```env
WHATSAPP_ENABLED=true
WHATSAPP_USER_MAPPINGS=919876543210|38|3|Display Name
WHATSAPP_REQUIRE_ALLOWLIST=true
WHATSAPP_ALLOW_UNSIGNED_WEBHOOKS=true
WHATSAPP_MAX_WEBHOOK_BYTES=262144
WHATSAPP_RATE_LIMIT_PER_MINUTE=30
WHATSAPP_IP_RATE_LIMIT_PER_MINUTE=300
WHATSAPP_MAX_CONCURRENT_TASKS=10
```

Run `alembic upgrade head` from `efacility-chatbot/backend` after pulling this
version. WhatsApp identities are supplied through `WHATSAPP_USER_MAPPINGS`;
unknown senders and legacy `phone:name` mappings are rejected.

`WHATSAPP_ALLOW_UNSIGNED_WEBHOOKS=true` is an explicitly logged temporary
exception. Payload authenticity is not guaranteed until Meta App Secret
signature verification is added; keep the public webhook behind HTTPS and a
rate-limiting reverse proxy in the meantime.

Configure seat backend auth in `backend/.env`:

```env
ENABLE_SEAT_BACKEND_API=true
SEAT_BACKEND_API_URL=https://3284lwcmc1.execute-api.ap-south-1.amazonaws.com
SEAT_BACKEND_REFRESH_TOKEN=<refresh_token from browser cookies>
SEAT_BACKEND_ACCESS_TOKEN=
SEAT_BACKEND_SESSION_TOKEN=
SEAT_BACKEND_TOKEN_CACHE_PATH=.seat_backend_tokens.json
SEAT_BACKEND_REFRESH_INTERVAL_SECONDS=840
```

The backend refreshes auth before the 15-minute token window expires and calls `/auth/me` to identify the seat-backend user. Seat-backend token values are also read from the mounted `backend/.env` file at request time, so token edits can be picked up by the running API without rebuilding the container.

If you deliberately update token values in `backend/.env`, restart the API or use Restart Chat in the browser. The newer `.env` values will be preferred over the token cache.

Legacy combined cookie format is still supported:

```env
SEAT_BACKEND_AUTH_COOKIE=access_token=...; refresh_token=...; session_token=...
```

## Quick Book Ranking

Quick Book uses the external backend data available for the current token/user.

Priority:

1. Favorite/preferred seat ids from `/preferences`.
2. Most frequently booked seat from booking history.
3. Most frequently used site/building/floor.
4. Most recent booking as a tie-breaker.

If a preferred seat is available for the selected date, the chatbot selects it automatically and shows the confirmation card. If no preferred seat is available, it shows fallback available seats.

## Rebook Flow

Past booking cards include a `Rebook` action. The chatbot reuses the selected booking's site, building, floor, and seat, then shows a calendar:

- Green: same seat is available.
- Red: same seat is unavailable.
- Orange: user already has a booking that can be changed to the same seat.
- Purple: user already has a booking and the same seat is unavailable, so recommendations or available alternatives are used.

Month changes update the same calendar message in place, keeping the experience smooth on mobile.

## Mobile And Regression Coverage

The frontend includes a Playwright responsive suite under `frontend/tests/responsive`. It validates representative iOS and Android viewport profiles from older compact devices through modern large phones and tablets.

Covered UI areas:

- Chatbot launch, name entry, main menu, input/footer visibility.
- Booking card layout and future/today date highlighting.
- Rebook calendar green, red, orange, and purple states.
- Horizontal overflow prevention across all supported viewport profiles.

The Docker frontend image installs Chromium through `frontend/Dockerfile`, so the responsive suite can run after container rebuilds.

## Local Database Scope

Local chatbot-owned tables:

- `chatbot_sessions`
- `chatbot_messages`

Session flow context is stored in `chatbot_sessions.context_data` as JSONB.
Menus are code-defined and WhatsApp identities come from configuration.

Not stored locally:

- sites
- buildings
- floors
- seats
- amenities
- seat bookings
